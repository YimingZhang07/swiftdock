## Unattended snapshot follow-up (2026-10-15)

The reviewer approved the coverage mapping, measured `Validate.ps1` at 6.4 seconds with 453/453 passing, and E2E at 11/11 in 125 seconds. The E2E duration is accepted; its scenarios and the unit suite are unchanged by this follow-up. The counts/line measurements below describe the original consolidation before the renderer fix.

The old renderer called the product's modal delete-confirmation service before it could reach capture/close. The replacement constructs the same WPF-UI MessageBox and calls base `Window.Show` non-modally, then closes it programmatically. Every window is configured before handle creation with `ShowActivated=false`, no taskbar/topmost state, manual offscreen positioning, blocked keyboard-focus requests and native `WS_EX_NOACTIVATE`. A native position hook keeps later load/DPI repositioning outside the entire virtual desktop. The icon popup's actual child tree is hosted offscreen; the context menu is a standalone offscreen presentation root (including its decoration margin), without setting either popup's `IsOpen` or taking mouse capture.

A plain WPF `Application` loads the resource dictionary from a build-embedded copy of the product's `App.xaml`. It never constructs the product `App`, whose [base constructor queues startup](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Application.cs) even without `Run`. The renderer calls `Application.Run` so `Shutdown` actually ends the message loop. Configuration writes and login registration are in-memory, and favicon fetching is disabled.

Each of the unchanged 33 PNG targets runs in a separate worker, with a six-second deadline covering resource/DI setup, icon/preview work, layout, encoding and disposal. A timeout kills that worker, releasing its HWNDs even if the dispatcher is blocked, records the filename/error/last phase and proceeds to the next target. Ordinary failures follow the same continuation path. There are still no behavioral or pixel assertions.

The coordinator creates `snapshots.json` before workers start, records `expected`, `rendered`, `failed`, `current`, timestamps and completion state, and replaces it after every image. `Snapshots.ps1` creates an initial manifest even before restore/build and imposes a 90-second renderer deadline (`-TimeoutSeconds` overrides it). On overall timeout it stops only that coordinator PID; a kill-on-close Windows job also removes all its workers. The script reports the interrupted image, records all unrendered targets as failures, preserves completed entries, and exits non-zero. No `Start-Process -Wait` or unbounded wait on a modal dialog remains.

Verification: snapshot Release build with `-warnaserror` passed; the complete matrix and a forced one-second timeout were exercised using the real renderer, with no probe programs. The forced timeout identified `settings.png`, preserved 1 rendered/32 failed entries, and left zero renderer processes. Final run: **33 rendered, 0 failed, 35.049 s**, exit 0, with zero renderer processes remaining. Both delete confirmations, both menu themes, icon picker, launcher and settings PNGs were visually inspected. `Validate.ps1`: **5.797 s**, Release build 0 warnings/errors, **447 passed / 6 failed / 453 total**; the failures are the same sandbox `File.Replace` and named-pipe access failures listed below. Commands used the cached SDK/packages with `NuGetAudit=false` in the invoking environment. No unit/E2E cases, packages or git-index entries changed. ## Snapshot contract

Run `scripts/Snapshots.ps1` on an unlocked desktop. It restores/builds `QuickLaunch.Snapshots`, loads the actual app resource definitions into a plain `Application` without constructing the product `App`, uses isolated configuration/icons, disables network icon fetches, does not register hotkeys/tray/login startup, and renders the actual views. No synthetic mouse/keyboard input or external item launches are needed.

The output matrix under `artifacts/validation/` is:

- `launcher`, `settings`, `add-dialog`, `edit-dialog`, `name-dialog`, `icon-picker`, `item-menu`, `delete-confirm`, each with `.png` (dark) and `-light.png` (16 files).
- `appearance-{dark|light}-{blue|purple}-{acrylic|mica|solid}.png` (12 files).
- `appearance-settings-{dark|light}-{blue|purple}.png` (4 files).
- `panel-polish.png` (1 file).

`snapshots.json` continuously records rendered/failed lists, the current image, completion and capture limitations, including partial failure. PNGs are 96-DPI WPF `RenderTargetBitmap` compositions on the theme background; they do not capture DWM blur, native border or shadow. OS appearance fallback is respected. Old PNGs from prior runs are not evidence of a successful current run; use the manifest. Rendering failure returns a nonzero exit code, but no geometry, color, template or behavior assertions run here. E2E's actual-screen color sampling and DWM checks serve a different purpose.
